* [Keep fpa-api as the middleware between FullstackFreestyleTools and our apps](/decisions/01M849PZNBY4Z0P66KKNR0CY97.md) - fpa-events and fpa-profiles keep calling fpa-api, not FullstackFreestyleTools directly. Reasons: we control our own API contract while the upstream changes owner and shape; the last-good snapshot keeps serving when upstream is down; fpa-profiles' export stays merged in place; stats, alias merging and division normalization stay in one tested place; one occasional sync client is the lightest load on the upstream. Scaling, if ever needed, is a cache-header and reverse-proxy (Cloudflare) concern. Alternative considered: apps call a public data API on FullstackFreestyleTools directly and fpa-api is retired — rejected: loses control of the contract and the outage buffer, and moves our derived features into each app.
* [Add a sync API to FullstackFreestyleTools ourselves and submit it as a PR](/decisions/01M849PZR193Z350KXFHFYNFMV.md) - We implement what fpa-api needs as /api/v1/sync/* in FullstackFreestyleTools on our fork (fluid-movement/FullstackFreestyleTools) and submit it to SmilesAir/FullstackFreestyleTools as a PR, rather than asking Ryan to build anything. The endpoints are shaped for keeping a mirror up to date (a manifest of hashes, batched full events, the player list), not for page views; the earlier consumer-shaped branch claude/public-data-api is not reused. Rankings and ratings keep coming from the existing Points API (getManifest, downloadPointsData). Alternative considered: make the new API return the old services' payload shapes — rejected: it would recreate their quirks (non-contiguous round keys, poola/poolA, alias chains, two points shapes) on purpose; fpa-api adapts clean payloads in its upstream layer instead.
* [Serve finished events only; no live or in-progress data](/decisions/01M849PZTAH4QVGREDHMC754DE.md) - The sync API lists only events that are over and locked in; fpa-api never serves an event while it is being judged. This replaces the judging-service probes (getEventDirectory, getEventDataVersion, getEventData), the pool-lock withholding and CONSUME_IN_PROGRESS_EVENTS. The exact rule for 'finished' is still open on the issue.
* [Incremental sync by content hash per event](/decisions/01M849PZWK8E0PHPB80DC4XTMA.md) - FullstackFreestyleTools has no updated_at on players, events, divisions or teams, so 'changed since' cannot be asked. The sync manifest carries one hash per finished event (over exactly the payload sync/events returns, built by the same query so the two cannot disagree) and one hash for the player list. fpa-api polls the manifest, fetches only new or changed events in batches, drops events that left the manifest, and refetches players when their hash changes. Hashes also catch deletions and later corrections, which an updated_at column would miss for deletes. Teams carry raw player ids and players carry aliasId, so an alias merge changes only the players hash, not every event that player played in. Alternative considered: add updated_at columns and triggers to FullstackFreestyleTools — rejected: schema changes across every write path of someone else's app, and deletes still go unseen.
* [Switch production after Ryan migrates the historic data](/decisions/01M849PZYWGWM5ARSQHQQQBPN7.md) - The new upstream is built and kept working on feature/new-api once the sync PR is accepted, but production keeps reading the old AWS services until Ryan has migrated the historic data into FullstackFreestyleTools (asked, pending). Then fpa-api switches fully; there is no period of reading from both.
* [Finished event: past, not playing, not a test, fully placed](/decisions/01M84A0B317QBYK3E56FAQCZ59.md) - The sync API lists an event when it is not a test event, is_playing is false, its end_date is before today, it has at least one visible division (is_hidden not true) with teams in rounds 1+, and every team in rounds 1+ of its visible divisions has a place. Pool locks are not used: a missing pools row reads as unlocked and imported events have none. events.is_hidden (hidden from the Rankings Generator) does not exclude an event; the Points API includes such events too.
* [Sync API sends hidden players flagged; fpa-api applies the policy](/decisions/01M84A0B5KMHKPDYB049HH77P5.md) - sync/players includes hidden players with hidden: true, because teams reference them and leaving them out would leave holes in line-ups. fpa-api leaves hidden players out of player lists, search and matching, and keeps them by name in placements. Personal fields (gender, membership) are not part of the sync API.
* [Remove live and CONSUME_IN_PROGRESS_EVENTS from fpa-api](/decisions/01M84A0B8RCH4PCD0744ZCBGK6.md) - With finished events only, fpa-api drops the live field from /health, the judging probes, the in-progress withholding and the CONSUME_IN_PROGRESS_EVENTS setting. fpa-events and fpa-profiles do not read live (checked), so no compatibility period is kept.
* [Adapt sync payloads into the existing Raw* types first](/decisions/01M84A0BBZPJC0PYR6DNDC5TBC.md) - fpa-api's new upstream layer converts sync payloads into the existing Raw* corpus types, so the domain normalizers and their tests stay untouched and the change is confined to upstream, store, scheduler, snapshot and config. Simplifying the Raw* types to the clean sync shapes is a later, separate step.
* [In-memory read model, no database, no writes](/decisions/in-memory-read-model.md) - Why the corpus lives in RAM, the service is read-only and the snapshot stores raw rather than derived data
